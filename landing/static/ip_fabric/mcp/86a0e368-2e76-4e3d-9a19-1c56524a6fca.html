00 The headline finding

The MCP server is a guardrail on the assistant, not a boundary on the token

Everything reachable through MCP today is read-only, and that is genuinely useful: it stops an AI assistant from mutating your network. But it does not down-scope the credential. The API token you hand the MCP server keeps every privilege its RBAC role grants the moment it is used anywhere else.

■ The real boundary

Scope the token to a read-only role

The token’s RBAC role is the only thing that actually limits it; the Callable flag just mirrors that role. An admin token stays full-privilege the moment it is used outside MCP (raw /api/ via curl), writes included. IP Fabric should ship a preconfigured read-only “mcp” role, built on read-only policies, and steer customers to it so the default is not an admin token, which is what most will reach for (as we did here).

▚ The guardrail

The MCP tool surface

The generic invoke tool looks like it can write: its options list PUT, DELETE and PATCH. But the server only knows the endpoints it was built with, and those are all reads: GET requests and POST /tables queries. Ask for anything else and it answers not found. So the assistant has no write to make, whatever the token allows.

01 Server & access model

How it answers, and what it checks

The endpoint speaks JSON-RPC 2.0 over a single POST /mcp (an Express backend that proxies internally to https://localhost/api/). GET /mcp is rejected. It advertises tools, prompts and resources, each with listChanged: true.

The discovery plane is open; the data plane is not. Every method that lists capabilities or reads a resource returns 200 with no Bearer token, so the full tool schemas, the prompt template, and the internal playbook text are readable by anyone who can reach the URL. Authentication only bites when a tool executes: tools/call without a token returns 200 at the HTTP layer but an isError result (“No authentication credentials provided”), and a valid token is then gated by its RBAC role. No device, snapshot, or config data leaks unauthenticated.

Risk: unauthenticated information disclosure. The MCP Authorization spec (protocol 2025-06-18) says an HTTP-transport server should protect the endpoint and answer unauthenticated requests with 401 + WWW-Authenticate; here there is no challenge header and no OAuth discovery metadata. Leaving list/read open is a very common implementation pattern (many MCP servers guard only the tool calls that carry data or side-effects), so this is not unusual, but it is still information leakage: an anonymous caller can fingerprint the IP Fabric instance and its MCP version and pull the internal playbooks (workflow logic, env-flag names). No network data is exposed, so the severity is recon-grade, not a data breach.

Mitigation in your control: restrict network reach to /mcp at the reverse proxy (IP allowlist / VPN / mTLS), since discovery itself is unauthenticated; and raise the missing 401 with IP Fabric as a hardening request.

Optional: destination, group, protocol (strict enum TCP | UDP | ICMP). It adapts wording to unicast / multicast / host-to-gateway based on which inputs you supply.

05 Endpoint enumeration

Enumerated 472 via the MCP tool; the OAS confirms all 472 are reads

The MCP server never serves its spec, so the surface was first enumerated indirectly: unioning ~12 broad ipf_api_endpoint_search queries (each limit 5000) and de-duplicating gave 472 unique endpoints (96 GET + 376 POST/tables). That figure was then cross-checked against the authoritative spec.

Write-safety is confirmed, not just inferred. The enumerated read count matches the OAS exactly (96 GET and 376 POST/tables in both), so the search-union turned out complete for the read surface, not a lower bound. The 194 writes the full API defines (104 non-table POST, 44 DELETE, 25 PATCH, 21 PUT) are provably absent from the MCP index: calling ipf_api_endpoint_details with the exact OAS paths (e.g. DELETE /api-tokens/{key}, PUT /attributes/global, POST /api-tokens) returns API endpoint not found. So the MCP server deliberately ingests only the read surface, and no admin token changes that.

06 Token security notes

Treat the MCP token as a full API credential

  • The token is an ordinary IP Fabric API token supplied as Authorization: Bearer <token>. MCP does not sandbox or attenuate it.
  • Its power is defined entirely by its RBAC role. The admin token tested reaches the entire read surface; the same token against raw /api/ retains whatever writes the role permits, outside MCP’s guardrail.
  • Scope the token to a read-only role if the assistant only needs to observe. That, not the MCP surface, is what limits blast radius if the token leaks.
  • Metadata (tools/prompts/playbooks) is exposed without auth, informative to anyone who can reach /mcp. Restrict network access to the endpoint accordingly.
  • If wired into a client as a registered server (e.g. .mcp.json / claude mcp add), the token sits in that config in plaintext, so prefer a read-only-role token or an env-var reference there.

Bottom line. The read-only property protects you from the AI going rogue, not from a leaked credential. If this token escapes, it is a full-privilege admin key.

A Appendix

The six playbooks, expanded

These Markdown resources are the assistant’s built-in operating manual, read via resources/read against each ipfabric:// URI (no auth required). They are guidance for the model, not network data.

1 · general-mcp-tools-usage

ipfabric://playbooks/general-mcp-tools-usage

The master routing algorithm every request passes through. Priority rule: if a question touches network issues, intent, or routing, start with ipf_network_health_assess. Otherwise a decision table maps need → tool (path between IPs → unicast; host→gateway; multicast; anything else → search + invoke).

  • Mandates fetching a real snapshot UUID first (GET /snapshots); never placeholder IDs.
  • Path-lookup defaults: protocol: icmp, firstHopAlgorithm: automatic, groupBy: siteName.
  • Keep includeGraphLayout off unless the user asks for visual layout data.

2 · api-discovery-workflow

ipfabric://playbooks/api-discovery-workflow

The generic-data pattern: search → details → invoke. Emphasises natural-language queries (semantic embeddings), then reading the endpoint schema before invoking, then server-side filtering rather than fetching-then-filtering.

  • Query strategy table (device / interface / routing / site / VLAN / performance) with good-vs-bad examples.
  • Use columns, filters (["eq","HQ"]-style), pagination, and responseKeys to trim payloads.
  • Worked examples: device inventory, BGP neighbours, interface errors, with iterative refinement guidance.

3 · general-snapshot-handling

ipfabric://playbooks/general-snapshot-handling

Everything about snapshots: UUID vs name, the state (loaded/unloaded/…) and status (done/run/error/…) fields, and a Canonical Snapshot Selection Algorithm.

  • Usability predicate: state == "loaded" && status == "done"; pick highest tsEnd for “latest”.
  • Name → UUID resolution is client-side (exact, then case-insensitive contains; disambiguate on multiple matches).
  • $last is the shortcut for “latest / current / most recent”.

4 · network-health-ai-agent-guide

ipfabric://playbooks/network-health-ai-agent-guide

How to drive ipf_network_health_assess: call it first, branch on overallHealth (CRITICAL → present + offer investigation; REQUIRES_ATTENTION → prioritise warnings; HEALTHY → confirm + offer proactive checks).

  • Target areas via sections {intent, inventory, routing, pathChecks}; filter by severityFilter.
  • Deep-dive recipes: routing (BGP/OSPF not-established), device (recent reloads via uptime), path validation.
  • Prefer Markdown output for users; don’t dump raw JSON.

5 · pathlookup-analysis

ipfabric://playbooks/pathlookup-analysis

Selecting and running the path-lookup tools, with a standard output format (why-selected → hop-by-hop → health ✅/❌ → ≤3 recommendations).

  • Image-content awareness: honour IPF_MCP_ENABLE_IMAGE_CONTENT; never emit raw base64 / data:image payloads.
  • Operation limits: 1 primary lookup + ≤2 enrichment calls; ≤5 findings, ≤3 recommendations.
  • Common failure causes checklist: missing route, ACL/firewall drop, device excluded, RPF failure, ARP/gateway.

6 · general-error-handling

ipfabric://playbooks/general-error-handling

Graceful-failure guidance by error category, with ready-made user-facing responses.

  • Auth (401/403): report the failure, suggest checking token config/expiry/permissions, and explicitly do not retry with different tokens.
  • Snapshot (404 / not found / empty): diagnose name-vs-UUID, list snapshots, offer $last or a chooser.
  • Frames each failure as an actionable next step rather than a raw stack trace.

Methodology & caveats

All findings gathered by speaking the MCP wire protocol directly, hand-issued JSON-RPC 2.0 over POST https://marketing.ipf.cx/mcp with the token in the Authorization header, not via a registered MCP client. Scope was deliberately limited to the MCP-exposed, read-only endpoints; no user-admin, system-admin, or mutating calls were made. Endpoint totals were first enumerated by unioning multiple broad ipf_api_endpoint_search queries (limit 5000) and de-duplicating, then cross-checked against the published OAS at /api/static/oas/openapi-internal.json (OpenAPI 3.1.0, v8.0). The cross-check confirmed the union was complete for the read surface (96 GET + 376 POST/tables in both). Write-safety is confirmed against that spec: the 194 write operations it defines (non-table POST, DELETE, PATCH, PUT) return API endpoint not found from ipf_api_endpoint_details even with their exact OAS paths, so no write was ever attempted.
