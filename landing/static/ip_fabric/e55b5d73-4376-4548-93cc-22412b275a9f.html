Executive Summary

Subject to review

A downloaded IP Fabric snapshot is an unencrypted archive of collected network state, in plain JSON (JavaScript Object Notation). Its vault does encrypt the credentials it uses to log in: device passwords and API tokens are AES-256, and UI logins are bcrypt. That protection holds inside the snapshot too. The stored login username is ciphertext, and the password field is null. What the snapshot does not redact is the material it reads out of the devices' own configs. That means SNMP community strings, password and enable-secret hashes, local usernames, and AAA server addresses. It also means any free-text an operator typed into a credential note. This is expected, by-design behaviour, not a product flaw (see the documentation check on page 2). The operational point is simple: a snapshot is config-bearing, so treat it as sensitive.

Top findings, ranked, and qualified for this lab

1

A shared device password was recovered from its hash Demonstrated

The one $1$ MD5crypt hash reused across ~40 devices cracks to vagrant; we verified it with openssl passwd -1 in milliseconds. Here it's a known netlab default on isolated devices, so nothing real is unlocked. In production the same pattern (one weak, reused secret) means crack-once, own-the-fleet.

2

A real password sits in a cleartext credential note Disclosure

The vault encrypts the username and nulls the password, but an operator typed "clab@123" into the free-text notes field, mapped to the platforms it unlocks. The encryption is bypassed by human habit, not by a flaw.

3

SNMP community strings, including read-write, in cleartext Not reachable here

Config shows private rw / public ro. Exploiting SNMP needs UDP/161 reachability; these devices sit on an isolated RFC1918 lab network, so it's moot for this demo. On a reachable production device an RW community means config rewrite and running-config exfil with no login.

4

IPs, AWS IDs and contact fields are low-value here Informational

The "public" IPs are mostly simulated / re-used ranges in a virtual lab, not reachable targets; AWS account IDs are a recon data point, not an attack (the API key/secret are encrypted); and admin@customer.com is a placeholder, not a person. Each is qualified on page 2.

Recommendation. Treat every snapshot as secret-bearing and keep it inside its trust boundary. Sharing a snapshot across a trust boundary should be a deliberate, low-risk-only decision weighed against the assets in play. For anything beyond a synthetic lab, scrub SNMP communities, credential-store notes and config hashes first, and hold snapshots on encrypted storage (IP Fabric encrypts the VM's data at rest at the storage layer, not the exported file). Archive Structure

Page 1 / 2

Each snapshot is a plain .tar holding two things: a gzipped data.tgz of collected network state, and a meta/ directory of collection metadata. The .tar container is not encrypted; every payload is JSON or newline-delimited JSON (NDJSON), readable with tar + gunzip + jq. Vault-managed credentials inside it (login username, AWS API key/secret) are the exception, those remain encrypted.

Disclosure Findings & Real-World Risk

Page 2 / 2

✓ Validated against IP Fabric documentation

  • Device credentials & 3rd-party tokens (device passwords, API keys, jumphost creds) are encrypted with AES-256, key derived from the license, installation-specific.
  • IP Fabric UI user passwords are hashed with bcrypt and cannot be decrypted.
  • Passwords at rest in the database and the techsupport archive are encrypted, "the whole techsupport archive is encrypted." A downloaded snapshot is a different artifact and is not wrapped in that encryption.
  • The VM is deliberately not app-encrypted; IP Fabric recommends encryption at the storage layer (e.g. VMware datastore).
  • Discovery is read-only CLI (SSH/Telnet), with no SNMP polling, so SNMP community strings appear only because they were read out of show running-config.

What this means for our findings: everything we observed is consistent with the documented model. The vault protects the credentials IP Fabric stores and uses; it does not, and is not designed to, redact secrets embedded in the customer's own device configs that discovery captures. The masking asymmetry below is that design, not a defect. Sources: docs.ipfabric.io FAQ, ipfabric.io FAQ.

The masking asymmetry, expected, by design

IP Fabric redacts the credentials it injects at login and stores in its vault, but not the secrets it harvests from device output. That line is exactly where the documented vault boundary sits, useful to know, not a defect to file.

✓ Encrypted / masked (vault-managed)

  • Login username & password reply in the raw CLI stream → <password>
  • Credential-store username → AES ciphertext; password → null
  • AWS apiKey / apiSecret → encrypted blobs

✗ Stored as collected (device-config content)

  • SNMP community strings (incl. rw) from config
  • Password / enable-secret hashes
  • Operator notes, where a real password can appear
  • Local usernames & AAA server IPs in parsed devices/

Bottom line. These are synthetic netlab snapshots, so nothing here is a live exposure; the value is in seeing precisely what the format keeps and what it drops. The one thing that generalises directly is behavioural, not technical: a snapshot faithfully carries every secret in the devices' running configs, unencrypted, in a file that is easy to open. Keep snapshots inside their trust boundary; move one across a boundary only as a deliberate, low-risk-only decision judged against the assets in play, and scrub SNMP communities, credential notes and config hashes before you do.
